# 工作队列

## 1 概念

工作队列（workqueue）是一种转移任务执行环境的工具，例如当系统产生一个中断时，我们可以在中断处理函数里做一些紧急地操作，然后将另外一些不那么紧急，而且需要一定时间的任务封装成函数交给工作队列执行，此时该函数的执行环境就从 中断环境 变成了 线程环境，这就是 Linux 里经常提及的中断处理 "下半部"。

> **一句话总结**：把任务从"中断环境"搬运到"线程环境"执行。

---

## 2 为什么需要工作队列 —— 中断的"上半部"与"底半部"

中断处理程序中，会将该中断分割为两部分：

| 部分 | 运行环境 | 职责 | 要求 |
|------|----------|------|------|
| 上半部（Top Half） | ISR 中断环境 | 读硬件寄存器、清中断标志、发信号量通知 | 越短越好，不可阻塞 |
| 底半部（Bottom Half）| 线程环境 | 解析数据包、写文件、复杂计算等耗时操作 | 可被抢占 |

**工作队列就是实现"底半部"的机制之一**。与信号量 + 独立线程方案的对比：

| 方案 | 机制 | 适用场景 |
|------|------|----------|
| 信号量 + 独立线程 | ISR 释放信号量 → 唤醒处理线程 | 有常驻处理线程，重复触发 |
| 工作队列 | ISR 提交工作项 → 工作队列线程执行 | 一次性任务，执行完即释放，提交即忘 |

工作队列的优势：不需要为每种底半部任务单独创建一个常驻线程，只需把函数"丢"进队列即可。

## 3 内部结构 —— 三个核心组件

### 3.1 工作项（work item）

工作项是对"要执行的函数"的封装，可以简单理解为**函数指针 + 参数的包裹**：

```c
struct rt_work
{
    rt_list_t list;              // 链表节点，用于挂在 worklist 上
    void (*work_func)(struct rt_work *work, void *user_data);  // 要执行的函数
    void *user_data;             // 用户自定义数据
    // ... 其他字段
};
```

### 3.2 工作链表（worklist）

是一条双向链表，把所有待执行的工作项串起来。**FIFO 顺序执行**，先提交的先跑：

```
  worklist_head
       │
       ▼
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ work #1 │───→│ work #2 │───→│ work #3 │───→ NULL
  └─────────┘    └─────────┘    └─────────┘
    ↑ 最先提交                          ↑ 最后提交
    (先执行)                            (后执行)
```

新的工作项追加到链表尾部，工作线程从链表头部取出执行。

### 3.3 工作线程（worker thread）

工作队列内部有一个专用线程，在死循环中轮询工作链表：

```
while (1) {
    从 worklist 取出一个 work_item;
    if (worklist 为空) {
        挂起自己（等待唤醒）;   // 不浪费 CPU
        continue;
    }
    执行 work_item->work_func(work_item, user_data);
}
```

关键设计：
- **队列为空时线程挂起**，不浪费 CPU
- **新工作项提交时唤醒线程**（通过完成量等 IPC 机制）
- 线程优先级通常设置得较低，不影响实时任务

## 4 完整工作流程

```
中断触发
    │
    ▼
ISR（上半部）           ← 中断环境，关同级中断
    │ 读硬件、清标志
    │ rt_workqueue_dowork()  提交工作项
    ▼
工作链表新增 work_item
    │ 唤醒工作线程（通过完成量）
    ▼
工作线程               ← 线程环境，可被抢占
    │ 执行 my_work_func()
    │ 复杂数据处理、写文件等
    ▼
完成，工作项释放
```

---

## 5 执行环境切换的意义

| 方面 | 中断环境（ISR） | 线程环境（工作队列） |
|------|-----------------|---------------------|
| 是否可被抢占 | 只被更高优先级中断抢占 | 可被任何高优先级线程抢占 |
| 能否阻塞 | ❌ 绝对不能（没有"当前线程"） | ✅ 可以 |
| 能否访问文件系统 | ❌ 危险 | ✅ 安全 |
| 能否分配内存 | 只能从紧急池 | 正常分配即可 |
| 栈空间 | 独立中断栈（有限） | 线程栈（充裕） |

**这就是"转移执行环境"的本质意义。**

## 6 典型 API 使用流程

### 6.1 创建工作队列

```c
struct rt_workqueue *workqueue;
workqueue = rt_workqueue_create("wq", 2048, RT_THREAD_PRIORITY_MAX - 2);
//                             名称    栈大小    优先级（通常设低一些）
```

### 6.2 初始化工作项

```c
struct rt_work work;

void my_work_func(struct rt_work *work, void *user_data)
{
    // 这里是底半部的实际处理逻辑
    int *val = (int *)user_data;
    // 做耗时操作...
}

rt_work_init(&work, my_work_func, &some_data);
```

### 6.3 提交工作项（在 ISR 中调用）

```c
// 在 ISR 中调用（中断上半部）
void isr_handler(void)
{
    // 紧急操作：读寄存器、清标志
    uint32_t status = READ_REG(STATUS_REG);
    CLEAR_FLAG(STATUS_REG);

    // 非紧急操作：丢给工作队列
    rt_workqueue_dowork(workqueue, &work);
}
```

## 7 设计要点

### 7.1 工作项是一次性的

工作项执行完后不会自动重新入队。如果需要周期性执行，需在 `work_func` 内部重新提交自己，或使用**定时器**。

### 7.2 工作项不可重复提交

同一个 work_item 如果已经 pending，再次 `dowork` 通常是无效操作。提交前需确认上一次执行已完成，或使用 `rt_workqueue_cancel_work()` 先取消。

### 7.3 与其它 IPC 机制的关系

```
工作队列 = 完成量（唤醒机制）+ 链表（任务队列）+ 线程（执行环境）
```

工作队列把"信号量 + 队列 + 线程"这个常见模式标准化了，避免每次手写样板代码。

## 8 在整个 RT-Thread 知识体系中的位置

```
中断机制
  ├── 上半部（ISR）：紧急、短促、不可阻塞
  └── 底半部：非紧急、耗时
        ├── 信号量 + 独立线程：适合有常驻处理需求的场景
        ├── 工作队列：适合一次性任务，提交即忘  ← 【这里】
        └── 完成量：常与工作队列配合，标记"某一项做完了"
```
