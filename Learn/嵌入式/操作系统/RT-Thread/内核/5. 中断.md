# 5.中断

# **Cortex-M CPU架构**
Cortex-M 系列 CPU 的寄存器组里有 R0~R15 共 16 个通用寄存器组和若干特殊功能寄存器，通用寄存器组里的 R13 作为堆栈指针寄存器 (Stack Pointer，SP)；R14 作为连接寄存器 (Link Register，LR)，用于在调用子程序时，存储返回地址；R15 作为程序计数器 (Program Counter，PC)，其中堆栈指针寄存器可以是主堆栈指针（MSP），也可以是进程堆栈指针（PSP）。

<blockquote style="color:red"><b>R0~R12 通用寄存器</b><br>
全部为 32 位。R0~R3 用于函数传参与返回值，属于"调用者保存"寄存器；R4~R11 用于函数内局部变量，属于"被调用者保存"寄存器（用完要恢复）；R12 为内部调用暂存寄存器（IP），用于长跳转等场景。中断发生时硬件会自动将 R0~R3、R12 压入中断栈。</blockquote>

![[Pasted image 20260812000540.png]]

#### 操作模式和特权级别
Cortex-M 引入了操作模式和特权级别的概念，分别为线程模式和处理模式，如果进入异常或中断处理则进入处理模式，其他情况则为线程模式。
![[Pasted image 20260812000556.png]]
- 线程模式可以工作在特权级或者用户级，而处理模式总工作在特权级，可通过 CONTROL 特殊寄存器控制。
- Cortex-M 的堆栈寄存器 SP 对应两个物理寄存器 MSP 和 PSP，MSP 为主堆栈，PSP 为进程堆栈，处理模式总是使用 MSP 作为堆栈，线程模式可以选择使用 MSP 或 PSP 作为堆栈，同样通过 CONTROL 特殊寄存器控制。复位后，Cortex-M 默认进入线程模式、特权级、使用 MSP 堆栈。

<blockquote style="color:red"><b>MSP 与 PSP 的关系</b>：SP（无论 MSP 还是 PSP）永远指向当前活跃栈的栈顶。可理解为 MSP 是系统级栈（中断 + 初始化前），PSP 是用户级栈（每个线程独立）。线程用 PSP 时，MSP"冻结"在中断栈位置；进入中断时 SP 强制切回 MSP。</blockquote>

#### 嵌套向量中断控制器
中断控制器名为 NVIC（嵌套向量中断控制器），支持中断嵌套功能。当一个中断触发并且系统进行响应时，处理器硬件会将当前运行位置的上下文寄存器自动压入中断栈中
![[Pasted image 20260812000610.png]]
当系统正在服务一个中断时，如果有一个更高优先级的中断触发，那么处理器同样会打断当前运行的中断服务程序，然后把这个中断服务程序上下文的 PSR、PC、LR、R12、R3-R0 寄存器自动保存到中断栈中。
#### PendSV系统调用
PendSV 也称为可悬起的系统调用，它是一种异常，可以像普通的中断一样被挂起，它是专门用来辅助操作系统进行上下文切换的。PendSV 异常会被初始化为最低优先级的异常。每次需要进行上下文切换的时候，会手动触发 PendSV 异常，在 PendSV 异常处理函数中进行上下文切换。

## 1.2 中断处理过程
中断处理程序分为中断前导程序、用户中断服务程序、中断后续程序三部分
![[Pasted image 20260812000636.png]]
#### 1）中断前导程序
主要内容如下：
1. 保存CPU中断现场
2. 通知内核进入中断状态，此时会把全局变量rt_interrupt_nest 加一表示记录中断嵌套的层数。
    ```
    void rt_interrupt_enter(void)
    {
    rt_base_t level;

    level = rt_hw_interrupt_disable();
    rt_interrupt_nest ++;
    rt_hw_interrupt_enable(level);
    }
    ```
#### 2）用户中断服务程序
用户中断程序（ISR）分为两种情况
1. 不需要进行线程切换，这种情况下中断服务程序和中断程序运行完毕后退出中断模式，返回被中断的线程。
2. 需要进行线程切换，这种情况会调用 rt_hw_context_switch_interrupt() 函数进行上下文切换

<blockquote style="color:red"><b>ISR 的两项职责</b>：① 完成中断对应的硬件任务（读外设数据、清标志位、发信号量等）；② 判断是否触发线程切换（通过 PendSV 间接完成，不直接做上下文切换）。<br><br>
<b>是否切换的判断标准</b>：取决于当前中断是否导致了一个更高优先级线程进入就绪状态（如 ISR 释放信号量唤醒了高优先级线程、SysTick 时间片用完等），而非"碰巧"发生。</blockquote>

**rt_hw_context_switch_interrupt()**
![[Pasted image 20260812000653.png]]
设置需要切换的线程 rt_interrupt_to_thread 变量，然后触发 PendSV 异常，PendSV 异常被触发后，不会立即进行 PendSV 异常中断处理程序，因为此时还在中断处理中，只有当中断后续程序运行完毕，真正退出中断处理后，才进入 PendSV 异常中断处理程序。
#### 3）中断后续程序
主要工作是：
1. 通知内核离开中断状态，通过调用 rt_interrupt_leave() 函数，将全局变量 rt_interrupt_nest 减 1
2. 恢复中断前的 CPU 上下文，如果在中断处理过程中未进行线程切换，那么恢复 from 线程的 CPU 上下文，如果在中断中进行了线程切换，那么恢复 to 线程的 CPU 上下文。

#### 4）中断嵌套
允许中断嵌套的情况下，在执行中断服务程序的过程中，如果出现高优先级的中断，当前中断服务程序的执行将被打断，以执行高优先级中断的中断服务程序，当高优先级中断的处理完成后，被打断的中断服务程序才又得到继续执行，如果需要进行线程调度，线程的上下文切换将在所有中断处理程序都运行结束时才发生。
#### 5）中断栈
在中断处理过程中，在系统响应中断前，软件代码（或处理器）需要把当前线程的上下文保存下来（通常保存在当前线程的线程栈中），再调用中断服务程序进行中断响应、处理。在进行中断处理时（实质是调用用户的中断服务程序函数），中断处理函数中很可能会有自己的局部变量，这些都需要相应的栈空间来保存，所以中断响应依然需要一个栈空间来做为上下文，运行中断处理函数。中断栈可以保存在打断线程的栈中，当从中断中退出时，返回相应的线程继续执行。

中断栈也可以与线程栈完全分离开来，即每次进入中断时，在保存完打断线程上下文后，切换到新的中断栈中独立运行。在中断退出时，再做相应的上下文恢复。

RT-Thread 采用的方式是提供独立的中断栈，即中断发生时，中断的前期处理程序会将用户的栈指针更换到系统事先留出的中断栈空间中，等中断退出时再恢复用户的栈指针。这样中断就不会占用线程的栈空间，从而提高了内存空间的利用率，且随着线程的增加，这种减少内存占用的效果也越明显。

<blockquote style="color:red"><b>两种中断栈方案对比</b></blockquote>

<table style="color:red">
<tr><th>方案</th><th>描述</th><th>优缺点</th></tr>
<tr><td>中断栈 = 线程栈</td><td>中断直接借用被中断线程的栈</td><td>实现简单，但每个线程栈都必须预留中断所需的最大空间，浪费内存</td></tr>
<tr><td>独立中断栈</td><td>所有中断共享一个系统级栈空间</td><td>线程栈只需满足自身调用深度，内存利用率高（RT-Thread 采用）</td></tr>
</table>

<blockquote style="color:red">可以把中断栈理解为所有线程共享的"临时工作区"：中断来了，当前线程的快照（R0~R3、R12、LR、PC、PSR）保存在线程栈，ISR 内部的函数调用嵌套则在独立的中断栈上执行，互不污染。</blockquote>

在 Cortex-M 处理器内核里有两个堆栈指针，一个是主堆栈指针（MSP），是默认的堆栈指针，在运行第一个线程之前和在中断和异常服务程序里使用；另一个是线程堆栈指针（PSP），在线程里使用。在中断和异常服务程序退出时，修改 LR 寄存器的第 2 位的值为 1，线程的 SP 就由 MSP 切换到 PSP。

#### 6）底半处理
当一个中断发生时，中断服务程序需要取得相应的硬件状态或者数据。通常需要将该中断分割为两部分，即上半部分（Top Half）和底半部分（Bottom Half）。
上半部分，取得硬件状态和数据后，打开被屏蔽的中断，给相关线程发送一条通知（可以是 RT-Thread 所提供的信号量、事件、邮箱或消息队列等方式），然后结束中断服务程序
而接下来，相关的线程在接收到通知后，接着对状态或数据进行进一步的处理，这一过程称之为底半处理

## 1.3 裸机与RTOS栈模型对比

裸机程序只有一个栈（MSP），所有函数调用、中断处理共用一块空间，SP 一辈子不换。RT-Thread 利用 Cortex-M 双栈机制（MSP + PSP），将裸机的"大一统栈"拆分为 **N+1 个独立栈**：

- **中断栈（MSP 指向）**：唯一且共享，仅中断/异常处理时使用
- **线程栈（PSP 指向）**：每个线程一块，是线程自己的"主栈"，函数调用全在其上

物理上中断栈与线程栈是**平级独立的内存区域**，靠 MSP/PSP 切换"换台"，而非嵌套关系。SP 指向谁，CPU 当前就在谁的"世界"里：

| 场景          | SP 指向        | 说明                                |
| ------------- | -------------- | ----------------------------------- |
| 线程正常运行  | PSP → 线程栈   | 线程自己的"主栈"，跟裸机用 MSP 一样 |
| 中断/异常触发 | MSP → 中断栈   | 切换到独立中断栈，ISR 调用链全在这  |
| 中断返回      | PSP → 线程栈   | 回到被打断的线程                    |
| 线程切换      | PSP → 新线程栈 | 换到另一个线程的"主栈"              |

MSP 和 PSP 只是两个指针，不是栈本身。指到哪块内存，那块内存就是当前活跃栈。裸机中断借用线程栈，每个线程栈必须预留中断最大深度 → 浪费内存；独立中断栈让线程栈只需满足自身调用深度，利用率随线程数增加越明显。

### PSP 指向栈顶而非栈首地址

PSP 就是线程的"裸机 SP"，**永远指向栈当前用到的地方（栈顶）**，随着函数调用动态移动，不是栈的起始地址：

```
stack_addr（首地址）→ ┌──────────────┐ 高地址
                     │  已废弃的帧    │
                     ├──────────────┤
          PSP（sp）→  │  当前函数帧    │ ← 栈顶，正在用
                     ├──────────────┤
                     │  未使用空间    │
                     └──────────────┘ 低地址
```

线程被切走时：`thread->sp = PSP`（存档当前位置）；切回时：`PSP = thread->sp`（从上次停的地方继续）。两者的区别：

| 字段                 | 存的什么       | 变不变                   |
| -------------------- | -------------- | ------------------------ |
| `thread->stack_addr` | 栈的起始地址   | 线程创建时定死           |
| `thread->sp` / PSP   | 栈当前跑到哪了 | 每多一层函数调用就往下走 |

### 线程表与 PSP 切换的协同

线程就绪链表（软件）负责"选谁跑"，TCB 里的 `sp` 字段（硬件指针快照）负责"往哪切"。两者协同流程：

```
1. SysTick/PendSV 触发
2. 硬件自动压栈 R0~R3,R12,LR,PC,PSR → 当前线程栈
3. 当前 PSP → 存档到 thread_A->sp
4. 调度器从就绪链表选最高优先级线程 → thread_B
5. thread_B->sp → 恢复为 PSP
6. 硬件自动出栈 → PC 跳转到线程B上次停下的位置
```

### 如何确定当前在哪个线程栈

RT-Thread 维护全局变量 `rt_current_thread`，永远指向正在运行的线程 TCB。PSP 一定落在当前线程栈范围内：

```c
rt_current_thread->stack_addr ≤ PSP ≤ rt_current_thread->stack_addr + stack_size
```

切线程和切 PSP 是同步的，两者永远不会对不上。

# 2 中断管理接口
为了把操作系统和系统底层的异常、中断硬件隔离开来，RT-Thread 把中断和异常封装为一组抽象接口
![[Pasted image 20260812000730.png]]
## 2.1 中断服务程序挂接
系统把用户的中断服务程序 (handler) 和指定的中断号关联起来，可调用如下的接口挂载一个新的中断服务程序：
```c
rt_isr_handler_t rt_hw_interrupt_install(int vector,
                                        rt_isr_handler_t  handler,
                                        void *param,
                                        char *name);
```
调用 rt_hw_interrupt_install() 后，当这个中断源产生中断时，系统将自动调用装载的中断服务程序
> [!] Note
> 注：这个 API 并不会出现在每一个移植分支中，例如通常 Cortex-M0/M3/M4 的移植分支中就没有这个 API。
中断服务程序是一种需要特别注意的运行环境，它运行在非线程的执行环境下，在这个运行环境中不能使用挂起当前线程的操作，因为当前线程并不存在。
## 2.2 中断源管理
通常在 ISR 准备处理某个中断信号之前，我们需要先屏蔽该中断源，在 ISR 处理完状态或数据以后，及时的打开之前被屏蔽的中断源。
屏蔽中断源可以保证在接下来的处理过程中硬件状态或者数据不会受到干扰，可调用下面这个函数接口：
```c
void rt_hw_interrupt_mask(int vector);
```
，相应的中断将会被屏蔽（通常当这个中断触发时，中断状态寄存器会有相应的变化，但并不送达到处理器进行处理）。

<blockquote style="color:red"><b>屏蔽中断源的真正目的</b>：防止同一个中断源在处理期间再次触发，导致读到一半的硬件状态被破坏。<br><br>
<b>屏蔽 ≠ 阻断高优先级中断</b>：屏蔽中断源 1 只关了这一个中断，更高优先级的中断仍然可以抢占，处理完后回到中断源 1 时屏蔽依然生效——这是 NVIC 硬件特性，非 RT-Thread 独有。<br><br>
⚠ <b>区分两个层次</b>：中断源屏蔽（NVIC 寄存器级，只关某一个）≠ 全局中断开关（PRIMASK 级，一刀切全关）。前者在 ISR 内用，后者在线程内用。</blockquote>

## 2.3 全局中断开关
全局中断开关也称为中断锁，是禁止多线程访问临界区最简单的一种方式，即通过关闭中断的方式，来保证当前线程不会被其他事件打断（因为整个系统已经不再响应那些可以触发线程重新调度的外部事件），也就是当前线程不会被抢占，除非这个线程主动放弃了处理器控制权。
```
rt_base_t rt_hw_interrupt_disable(void);
```
恢复中断
```
void rt_hw_interrupt_enable(rt_base_t level);
```

<blockquote style="color:red"><b>为什么需要一刀切关掉所有中断？</b>——保护线程级临界区。当一个线程在修改全局数据（链表、共享变量等）时，如果中途来了中断触发 PendSV 切走线程，另一个线程读到不一致的数据，后果不可预料。关掉全局中断 → 不会响应任何中断 → PendSV 不会触发 → 线程不会被换走 → 临界区代码变成原子操作。<br><br>
📌 <b>原子操作</b>：指一段代码执行期间不会被任何事件打断，要么全部执行完，要么根本不执行。全局中断开关是最简单粗暴的实现方式，后续还会深入学习其他锁机制。<br><br>
⚠ <b>区分两种屏蔽</b>：<br>
• 中断源屏蔽（<code>rt_hw_interrupt_mask</code>）→ ISR 内用，只关一个源<br>
• 全局中断开关（<code>rt_hw_interrupt_disable</code>）→ 线程内用，一刀切全关</blockquote>

## 2.4 中断通知
当整个系统被中断打断，进入中断处理函数时，需要通知内核当前已经进入到中断状态。
```
void rt_interrupt_enter(void);
void rt_interrupt_leave(void);
```
这两个接口分别用在中断前导程序和中断后续程序中，均会对 rt_interrupt_nest（中断嵌套深度）的值进行修改

但如果中断服务程序不会调用内核相关的函数（释放信号量等操作），这个时候，也可以不调用 rt_interrupt_enter/leave() 函数。

在上层应用中，在内核需要知道当前已经进入到中断状态或当前嵌套的中断深度时，可调用 rt_interrupt_get_nest() 接口，它会返回 rt_interrupt_nest。
```
rt_uint8_t rt_interrupt_get_nest(void);
```
## 2.5 中断与轮询
通常情况下，实时系统中更多采用的是中断模式来驱动外设。当数据到达时，由中断唤醒相关的处理线程，再继续进行后续的动作。

对于低速设备来说，运用这种模式非常好，因为在串口外设把 FIFO 中的数据发送出去前，处理器可以运行其他的线程，这样就提高了系统的整体运行效率

但是对于高速设备来说，系统开销会大大的浪费再线程切换上，会造成实时系统的数据吞吐量不足。

我们可以看出其中的一些关键因素：发送数据量越小，发送速度越快，对于数据吞吐量的影响也将越大。归根结底，取决于系统中产生中断的频度如何。当一个实时系统想要提升数据吞吐量时，可以考虑的几种方式：
1. 增加每次数据量发送的长度，每次尽量让外设尽量多地发送数据；
2. 必要情况下更改中断模式为轮询模式。同时为了解决轮询方式一直抢占处理机，其他低优先级线程得不到运行的情况，可以把轮询线程的优先级适当降低。
