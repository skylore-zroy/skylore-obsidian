# 0.设备和驱动之间的继承和衍生

# RT-Thread 内核对象继承与派生体系

## 1. 设计哲学：C 语言的面向对象（OOPC）

RT-Thread 虽然用 C 语言编写，但采用了**面向对象**的设计思想。C 语言本身不支持类和继承，RT-Thread 通过 **结构体嵌套（结构体包含）** 的方式模拟了继承机制。

核心原则：**子类结构体的第一个成员必须是父类结构体**。这样：
- 子类结构体的起始地址 = 父类结构体的起始地址
- 可以直接将子类指针强制转换为父类指针（向上转型）
- 父类的所有属性被子类天然继承

---

## 2. 万物之源：`struct rt_object`

定义于 `include/rtdef.h`，是所有内核对象的**根基类**。

```c
struct rt_object
{
    char       name[RT_NAME_MAX];   // 内核对象名称（字符串标识）
    rt_uint8_t type;                // 内核对象类型（rt_object_class_type 枚举值）
    rt_uint8_t flag;                // 内核对象状态标志（已初始化/未初始化等）
    rt_list_t  list;                // 双向链表节点（用于挂载到对象容器链表）
#ifdef RT_USING_MODULE
    void      *module_id;           // 所属模块 ID（动态模块加载功能启用时有效）
#endif
};
```

**各字段含义：**

| 字段 | 用途 |
|------|------|
| `name` | 对象名，最多 `RT_NAME_MAX`（默认 8）个字符，用于 `rt_object_find()` 按名查找 |
| `type` | 对象类别标签，是 `rt_object_class_type` 枚举值。bit7（`0x80`）为 1 表示静态对象 |
| `flag` | 运行时状态标志，如是否已初始化、是否挂起等 |
| `list` | 双向链表节点，将同类对象串联在 `rt_object_container[]` 对应的链表上 |
| `module_id` | 可选字段，标识该对象属于哪个动态加载的模块 |

## 3. 对象类型枚举：`rt_obje ct_class_type`

```c
enum rt_object_class_type
{
    RT_Object_Class_Thread       = 0,   // 线程
    RT_Object_Class_Semaphore    = 1,   // 信号量
    RT_Object_Class_Mutex        = 2,   // 互斥量
    RT_Object_Class_Event        = 3,   // 事件集
    RT_Object_Class_MailBox      = 4,   // 邮箱
    RT_Object_Class_MessageQueue = 5,   // 消息队列
    RT_Object_Class_MemHeap      = 6,   // 内存堆
    RT_Object_Class_MemPool      = 7,   // 内存池
    RT_Object_Class_Device       = 8,   // 设备（I/O 子系统入口）
    RT_Object_Class_Timer        = 9,   // 定时器
    RT_Object_Class_Module       = 10,  // 动态模块
    RT_Object_Class_Unknown      = 11,  // 未知类型（容器数组末尾哨兵）

    RT_Object_Class_Static       = 0x80 // 静态对象标志位（与上面各值进行 OR 运算）
};
```

> **静态 vs. 动态**：`type & 0x80` 为 1 表示通过 `rt_object_init()` 初始化的静态对象（编译时分配内存），为 0 表示通过 `rt_object_allocate()` 分配的动态对象（堆上分配）。`rt_object_detach()` 只从容器分离而不释放内存，`rt_object_delete()` 从容器分离且释放内存。

## 4. C 语言实现继承的具体方式

以 `rt_timer` 为例，展示标准的**结构体嵌套继承**：

```c
struct rt_timer
{
    struct rt_object parent;                       // ★ 第一个成员：继承自 rt_object

    // 以下是 rt_timer 自身的属性（派生类扩展）
    rt_list_t        row[RT_TIMER_SKIP_LIST_LEVEL]; // 跳表层级（用于定时器排序）
    void           (*timeout_func)(void *parameter); // 超时回调函数
    void            *parameter;                      // 回调函数参数
    rt_tick_t        init_tick;                      // 初始节拍数
    rt_tick_t        timeout_tick;                   // 超时节拍数
};
```

**类型转换宏（container_of 技术）：**

```c
// 根据成员地址反推容器（结构体）地址
#define rt_container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - (unsigned long)(&((type *)0)->member)))
```

这样就可以从 `rt_object` 的 `list` 节点反向获取对象所属的完整结构体指针，是 `rt_list_entry()` 宏的核心原理。

> **特例说明**：`rt_thread` 和 `rt_memory` 在部分版本中并未直接嵌套 `struct rt_object`，而是将其成员（`name`、`type`、`flag`、`list`）**展开写在结构体内**。这两种写法在内存布局上等价，但嵌套写法更清晰、更符合 OOP 惯例。

### 4.5 深入理解 `parent` 的嵌入机制

#### 4.5.1 `parent` 不是指针，是嵌入的结构体实体

这是最容易误解的地方。看 `rt_timer` 的定义：

```c
struct rt_timer
{
    struct rt_object parent;   // ★ 这不是指针！这是一个真实的结构体，嵌入在此
    // ...
};
```

**它与指针的区别：**

```c
// ❌ 如果是指针（RT-Thread 不是这样做的）
struct rt_timer_wrong {
    struct rt_object *parent;  // 这是一个指针，8 字节（64位），指向别处的 rt_object
    // parent 和 timer 在内存中是分离的两个对象
};

// ✅ RT-Thread 实际的做法（嵌入）
struct rt_timer {
    struct rt_object parent;   // rt_object 的全部字段就放在这里，占据约 20+ 字节
    // parent 的字段和 timer 自己的字段在同一块连续内存中
};
```

#### 4.5.2 内存布局图解

当我们创建一个 `rt_timer` 时，**只有一块连续内存**：

```
假设 rt_timer 的地址起始于 0x20001000：

0x20001000  ┌──────────────────────────┐
            │  parent.name[8]          │  ← struct rt_object 的开始
0x20001008  │  parent.type             │
0x20001009  │  parent.flag             │
0x2000100A  │  parent.list (prev/next) │
0x20001012  │  parent.module_id        │  ← struct rt_object 的结束
            ├──────────────────────────┤
            │  row[0] (链表节点)        │  ← rt_timer 自己的成员
            │  row[1]                  │
            │  ...                     │
            │  timeout_func            │
            │  parameter               │
            │  init_tick               │
            │  timeout_tick            │
            └──────────────────────────┘  ← rt_timer 的结束

注意：parent 的首地址 = rt_timer 的首地址 = 0x20001000
     （因为 parent 是结构体的第一个成员）
```

#### 4.5.3 `parent` 指向谁？——它不"指向"，它就是自己的一部分

> **核心结论：`parent` 不是指向"父对象"的指针，它是子对象身上的"父标签"。**

打个比方：
- C++ 的继承：子类对象内部包含一个隐式的父类子对象
- RT-Thread 的 `parent`：把这个父类子对象**显式命名**为 `parent`，放到结构体第一个位置



#### 4.5.4 向上转型：从子类到父类（直接强转，零开销）

关键原理：**第一个成员的地址 = 结构体本身的地址**（C 语言标准保证）。

```c
// 创建一个定时器
struct rt_timer my_timer;                     // 假设地址 = 0x20001000

// 向上转型：子类 → 父类
struct rt_object *obj = (struct rt_object *)&my_timer;
// obj = 0x20001000，和 &my_timer 完全相等！

// 等价写法（通过 parent 成员）：
struct rt_object *obj2 = &my_timer.parent;
// obj2 = 0x20001000，同样相等！

// 验证：以下三个值完全相同
// &my_timer == &my_timer.parent == (struct rt_object *)&my_timer
```

**内核中到处都是这种用法：**

```c
// src/object.c 中，rt_object_init 的实现（简化版）
void rt_object_init(struct rt_object *obj, enum rt_object_class_type type,
                    const char *name)
{
    // obj 实际上指向某个子类结构体的 parent 字段
    // 内核不管子类是什么，只操作其中的 rt_object 部分
    rt_strncpy(obj->name, name, RT_NAME_MAX);
    obj->type = type;
    obj->flag = 0;
    rt_list_insert_after(&container->object_list, &obj->list);  // 挂到容器链表
}

// 调用时：
struct rt_timer my_timer;
rt_object_init(&my_timer.parent, RT_Object_Class_Timer, "timer1");
//                        ↑
//              传递 parent 的地址，内核只看到 rt_object
```

#### 4.5.5 向下转型：从父类回到子类（依赖 `container_of` 宏）

当内核只持有 `rt_object *obj` 指针，但需要访问完整的子类时，使用 `container_of` 反推：

```c
// container_of 宏的原理
#define rt_container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - (unsigned long)(&((type *)0)->member)))

// 通俗解释：
// 1. ((type *)0)            → 假设在地址 0 处有一个 type 类型的结构体
// 2. &((type *)0)->member   → 计算 member 在 type 中的偏移量（编译时计算，不真正访问内存）
// 3. (char *)(ptr) - 偏移量 → 用实际 ptr 地址减去偏移量，得到 type 结构体的起始地址
// 4. (type *)               → 强转回 type 类型指针
```

**图解：**

```
场景：内核持有一个 rt_object *obj = (void *)0x20001000
      想知道它属于哪个 rt_timer？

已知：
  - obj 指向 rt_timer 内部的 parent 成员
  - parent 在 rt_timer 中的偏移量 = 0（因为它是第一个成员）

计算：
  rt_timer 的起始地址 = (char *)obj - parent 的偏移量
                      = 0x20001000 - 0
                      = 0x20001000

  ┌──────────────────────────────────────────────────┐
  │                                                  │
  │  obj ──────────────┐                             │
  │                    ▼                             │
  │  0x20001000  ┌──────────┐  ← parent 偏移量 = 0  │
  │              │  parent  │                        │
  │              ├──────────┤                        │
  │              │  row[0]  │  ← 偏移量 = 20         │
  │              │  ...     │                        │
  │              │  timeout │                        │
  │              └──────────┘                        │
  │  0x20001000 是 rt_timer 的起始地址 ◀─────────────┘
  │              （也是 parent 的地址）
  └──────────────────────────────────────────────────┘
```

**实际使用代码：**

```c
// src/timer.c 中 — 从 rt_object 反向获取 rt_timer
// rt_list_entry 是对 rt_container_of 的封装

// 场景：遍历定时器链表时
struct rt_object *obj = /* 从容器链表中获取 */;
struct rt_timer  *timer;

// 方式一：直接用 container_of（parent 偏移量为 0，实际等价于强转）
timer = rt_container_of(obj, struct rt_timer, parent);
//      = (struct rt_timer *)((char *)obj - offsetof(struct rt_timer, parent))
//      由于 parent 是第一个成员，offset = 0
//      = (struct rt_timer *)obj   ← 直接强转！

// 方式二：通过 list 节点反向查找（这才是最常见的场景）
// rt_timer 的跳表节点 row[i] 也挂在链表中
rt_list_t *node = /* 从定时器链表中获取 */;
struct rt_timer *timer2 = rt_list_entry(node, struct rt_timer, row[2]);
// 这里 row[2] 偏移量 ≠ 0，所以 container_of 真正发挥了作用
```

#### 4.5.6 `parent` 能指向子类吗？——可以，通过 `container_of`

> **`parent`（`rt_object`）本身不知道它属于哪个子类，但我们可以通过地址运算反推出来。**

这就好比：
- `parent`（`rt_object`）是身份证上的**姓名、编号**
- 内核对象容器通过身份证编号来**管理所有公民**（只知道编号和名字）
- 当需要找到具体的人（`rt_timer` / `rt_device` / `rt_thread`）时，通过 `container_of` 从身份证反推出**完整的人**

```c
// 一个典型的完整流程：

void demo(void)
{
    // === 1. 创建：创建一个 rt_timer ===
    struct rt_timer *timer = rt_malloc(sizeof(struct rt_timer));

    // === 2. 注册：以父类身份登记到内核 ===
    rt_object_init(&timer->parent, RT_Object_Class_Timer, "my_timer");
    //   内核将 &timer->parent 挂到 timer 容器链表
    //   内核不知道、也不关心它是一个 rt_timer —— 它只知道是一个 rt_object

    // === 3. 查找：按名称在容器中查找 ===
    struct rt_object *obj = rt_object_find("my_timer",
                                           RT_Object_Class_Timer);
    //   obj 返回的是 &timer->parent（即 rt_timer 内部的 rt_object 地址）
    //   由于 parent 偏移量为 0，obj == (struct rt_object *)timer

    // === 4. 向下转型：恢复为 rt_timer ===
    struct rt_timer *found_timer = (struct rt_timer *)obj;
    //   因为 parent 是第一个成员，(struct rt_timer *)obj 等价于 timer
    //   现在可以访问 found_timer->timeout_func 等专属字段了！
}
```

#### 4.5.7 总结三个核心问题

| 问题 | 答案 |
|------|------|
| **`parent` 是怎么嵌入的？** | 不是指针，是一个**真实的结构体实体**，所有字段直接分配在子类结构体的内存中 |
| **`parent` 指向谁？** | 不"指向"任何东西 — `parent` 就是子类自己身上的一块肉。它的地址和子类完全相同 |
| **能从 `parent` 回到子类吗？** | 能。当偏移量为 0（第一个成员）时，直接强转就行；当偏移量不为 0 时，用 `container_of` 宏做地址减法 |

**一句话总结**：`parent` 是子类结构体内部的"身份证件"——内核只认身份证管理所有对象，但当你需要找到具体的人时，身份证就贴在人的身上，找到身份证就等于找到了人。

### 4.6 `parent.list`：同类对象的链表串联机制

`rt_object` 中的 `list` 字段是一个双向链表节点。**每种类型的对象，都通过自己身上的 `parent.list` 节点，串联到 `rt_object_container[]` 中对应类型的容器链表上。**

#### 4.6.1 单条链表结构（以 Device 为例）

假设系统中注册了 3 个设备：`"uart1"`、`"spi1"`、`"i2c1"`。

```
rt_object_container[RT_Object_Class_Device]
    │
    ▼
┌─────────────┐
│   HEAD      │  ← 哨兵头节点
└──┬──────┬───┘
   │ prev │ next
   │      └──────────────────────────────┐
   ▼                                     ▼
┌──────────────────────────┐    ┌──────────────────────────┐
│  rt_device (uart1)       │    │  rt_device (spi1)        │
│  ┌────────────────────┐  │    │  ┌────────────────────┐  │
│  │ parent.name="uart1"│  │    │  │ parent.name="spi1" │  │
│  │ parent.type=Device  │  │    │  │ parent.type=Device  │  │
│  │ parent.list ◄═══════╫══╪════╪══╪════════════════════╪══╪═╗
│  └────────────────────┘  │    │  └────────────────────┘  │  ║
│  type      = Char        │    │  type      = SPI_Bus     │  ║
└──────────────────────────┘    └──────────────────────────┘  ║
                                                               ║
┌──────────────────────────┐                                   ║
│  rt_device (i2c1)        │                                   ║
│  ┌────────────────────┐  │                                   ║
│  │ parent.name="i2c1" │  │   ◄═══════════════════════════════╝
│  │ parent.list ◄═══════╫══╪══  （环形双向链表，最后一个指回头部）
│  └────────────────────┘  │
│  type      = I2C_Bus     │
└──────────────────────────┘
```

**关键点：**
- 所有设备挂在**同一条链**上，内核只认 `parent.list`，不关心外面是 `rt_serial_device` 还是 `rt_spi_bus`
- 每种对象类型（Thread、Timer、Device...）都有**自己独立的一条链表**

#### 4.6.2 多条容器链表并存全景

```
rt_object_container[]
    │
    ├── [Thread]    ──→ HEAD ⇄ thread1.parent.list ⇄ thread2.parent.list ⇄ HEAD
    ├── [Timer]     ──→ HEAD ⇄ timer1.parent.list ⇄ HEAD
    ├── [Semaphore] ──→ HEAD ⇄ sem1.parent.list ⇄ sem2.parent.list ⇄ HEAD
    ├── [Device]    ──→ HEAD ⇄ uart1.parent.list ⇄ spi1.parent.list ⇄ i2c1.parent.list ⇄ HEAD
    ├── [MemPool]   ──→ HEAD ⇄ pool1.parent.list ⇄ HEAD
    └── ...
```

> `list_device`、`list_thread` 等调试命令的原理就是遍历对应容器的链表，从每个 `parent.list` 用 `container_of` 反推出完整对象，打印 `parent.name`。

#### 4.6.3 链表操作流程

三个核心操作，都以 `parent` 为入口：

| 操作 | 函数 | 对 `parent.list` 的动作 |
|------|------|------------------------|
| **注册** | `rt_device_register()` → `rt_object_init(&dev->parent, ...)` | 填写 `name`/`type`，将 `parent.list` 插入容器链表 |
| **查找** | `rt_device_find("uart1")` → `rt_object_find(...)` | 遍历容器链表，比较每个节点的 `parent.name`，命中则返回 `rt_object *`，再强转为 `rt_device *` |
| **注销** | `rt_device_unregister()` → `rt_object_detach(&dev->parent)` | 将 `parent.list` 从容器链表摘除 |

#### 4.6.4 一句话总结

> **`parent` 承担了两重身份：一是"身份证"（`name` + `type`），二是"挂钩"（`list` 节点）。每个 `parent.list` 都是一节链条，把同类的所有对象串成一条双向链表，挂在 `rt_object_container[]` 中对应类型的容器之下。内核通过这条链管理万物。**

## 6. `rt_device` 设备基类详解

### 6.1 结构体定义

```c
struct rt_device
{
    struct rt_object parent;    // ★ 继承自 rt_object（第一个成员）

    // 设备分类与标志
    enum rt_device_class_type type;   // 设备类别（Char/Block/NetIf/SPI/I2C/...）
    rt_uint16_t               flag;  // 设备标志（只读/只写/流模式/DMA/中断等）
    rt_uint16_t               open_flag; // 打开标志

    // 引用计数与回调
    rt_uint8_t                ref_count;     // 引用计数（open 时+1，close 时-1）
    rt_uint8_t                device_id;     // 设备 ID（同类设备编号）

    // 数据收发回调（用于数据到达通知等）
    rt_err_t (*rx_indicate)(rt_device_t dev, rt_size_t size);
    rt_err_t (*tx_complete)(rt_device_t dev, void *buffer);

#ifdef RT_USING_DEVICE_OPS
    const struct rt_device_ops *ops;  // ★ 操作接口（新版通过指针挂载）
#else
    // 旧版：操作函数直接作为结构体成员
    rt_err_t  (*init)   (rt_device_t dev);
    rt_err_t  (*open)   (rt_device_t dev, rt_uint16_t oflag);
    rt_err_t  (*close)  (rt_device_t dev);
    rt_size_t (*read)   (rt_device_t dev, rt_off_t pos, void *buffer, rt_size_t size);
    rt_size_t (*write)  (rt_device_t dev, rt_off_t pos, const void *buffer, rt_size_t size);
    rt_err_t  (*control)(rt_device_t dev, int cmd, void *args);
#endif

    void *user_data;    // 用户私有数据（驱动程序可自由使用）
};
```

### 6.2 标准设备操作接口（`rt_device_ops`）

```c
struct rt_device_ops
{
    rt_err_t  (*init)   (rt_device_t dev);
    rt_err_t  (*open)   (rt_device_t dev, rt_uint16_t oflag);
    rt_err_t  (*close)  (rt_device_t dev);
    rt_size_t (*read)   (rt_device_t dev, rt_off_t pos, void *buffer, rt_size_t size);
    rt_size_t (*write)  (rt_device_t dev, rt_off_t pos, const void *buffer, rt_size_t size);
    rt_err_t  (*control)(rt_device_t dev, int cmd, void *args);
};
```

**接口说明：**

| 方法 | 功能 | 备注 |
|------|------|------|
| `init` | 设备初始化 | 设备注册时自动调用 |
| `open` | 打开设备 | ref_count++，可指定读写/阻塞等标志 |
| `close` | 关闭设备 | ref_count--，为 0 时可进入低功耗 |
| `read` | 读数据 | 块设备用 pos 指定偏移 |
| `write` | 写数据 | 块设备用 pos 指定偏移 |
| `control` | 设备控制 | ★ 核心扩展点，每种设备通过私有 cmd 实现差异化功能 |

> **`control()` 是设备扩展的核心机制**：每种设备类型（I2C、SPI、ADC、PWM 等）定义自己的命令字（cmd），通过 `control()` 统一入口实现各自特定的功能。这使得上层应用可以用统一的 API 操作所有设备，而底层差异被 `control` 的命令字消化。

### 6.3 设备类别枚举（`rt_device_class_type`）


## 7. I/O 设备模型的三层架构

RT-Thread 的 I/O 设备模型分为三个层次：

```
┌──────────────────────────────────────────────────────┐
│               应用程序层 (Application)                │
│   用户代码通过 rt_device_open/read/write/control     │
│   等统一 API 访问所有设备                              │
├──────────────────────────────────────────────────────┤
│             I/O 设备管理层 (Device Framework)         │
│   rt_device 基类                                      │
│   统一管理：注册、查找、打开、读写、关闭、控制          │
│   对象容器：所有设备按类别登记在 rt_object_container   │
├──────────────────────────────────────────────────────┤
│           设备驱动框架层 (Driver Framework)            │
│   各类设备的抽象驱动框架：                              │
│   ├── 串口框架 (serial)：缓冲区管理、数据收发          │
│   ├── SPI 框架：总线时序、片选管理                     │
│   ├── I2C 框架：起始/停止/应答时序                     │
│   ├── ADC/DAC/PWM 框架：通道管理、参数配置             │
│   ├── 传感器框架 (sensor)：传感器抽象、数据上报        │
│   └── ...                                             │
├──────────────────────────────────────────────────────┤
│             设备驱动层 (Hardware Driver)               │
│   与具体硬件相关的底层驱动代码（寄存器操作）            │
│   ├── stm32_uart.c / stm32_spi.c / stm32_i2c.c       │
│   ├── esp32_xxx.c / gd32_xxx.c / imx_xxx.c           │
│   └── ...                                             │
└──────────────────────────────────────────────────────┘
```

**关键流程——以串口设备为例：**

```
应用程序
  │ rt_device_open("uart1")        ← 统一 API
  ▼
I/O 设备管理层
  │ rt_device_find("uart1")        ← 按名称在容器链表中查找
  ▼
串口驱动框架 (serial.c)
  │ 缓冲区管理、DMA 控制、数据收发调度
  ▼
硬件驱动层 (stm32_uart.c)
  │ USART 寄存器操作、中断处理、DMA 配置
  ▼
硬件 (STM32 USART 外设)
```

---

### 7.1 驱动框架层的深度解析

三层架构中，设备管理层和设备驱动层都容易理解，中间的**驱动框架层**最容易困惑。它的核心定位是：**抽取同一类设备的共性逻辑，让硬件驱动只关注寄存器操作。**

#### 7.1.1 没有框架层会怎样？

以串口为例，环形缓冲、DMA 双缓冲、阻塞/非阻塞读写——这些逻辑跟具体硬件（STM32 / ESP32 / GD32）无关，但没有框架层时，每个芯片的驱动都要从头写一遍：

```
stm32_uart.c:  环形缓冲 + 阻塞读写 + DMA调度 + STM32寄存器操作
esp32_uart.c:  环形缓冲 + 阻塞读写 + DMA调度 + ESP32寄存器操作
gd32_uart.c:   环形缓冲 + 阻塞读写 + DMA调度 + GD32寄存器操作
                        ↑                          ↑
                  重复了 100 遍         唯一不同的就是这里
```

#### 7.1.2 框架层的解决方式

框架层提供**默认实现**（缓冲管理、DMA 调度、阻塞等待），硬件驱动只填写**与寄存器相关的回调函数表**。

以串口框架为例：

```
components/drivers/serial/serial.c   ← 框架层（只写一次，所有芯片共用）

    提供的是：
    - rt_serial_device 结构体（继承 rt_device + 内置收发环形缓冲）
    - 默认的 open / close / read / write 实现（缓冲管理 + 阻塞等待）
    - DMA 接收的通用调度逻辑（超时中断、FIFO 半满/全满处理）

    暴露给硬件驱动的注册接口：
    rt_hw_serial_register("uart1", &stm32_uart_ops, buf_size);
    //                      名字    硬件操作函数表      缓冲区大小

    硬件操作函数表（struct rt_uart_ops）只有寥寥几个回调：
     - configure(baud, parity, ...)  配置波特率/数据位/停止位
     - putc(ch)                      往硬件发一个字节
     - getc()                        从硬件读一个字节
     - start_tx() / stop_tx()        DMA 发送控制（可选）
```

```
stm32_uart.c   ← 硬件驱动（变得非常薄）

    只需实现 struct rt_uart_ops：
     - configure → 写 STM32 USART 的 BRR / CR1 寄存器
     - putc      → 往 DR 寄存器写一个字节
     - getc      → 从 DR 寄存器读一个字节

    然后一行注册：
    rt_hw_serial_register("uart1", &stm32_uart_ops, RT_SERIAL_RB_BUFSZ);
```

#### 7.1.3 调用链路对比

```
应用程序: rt_device_write("uart1", data, len)
    │
    ▼
设备管理层 (rt_device):
    统一 API → 找到设备 → 调用 dev->write(...)
    │
    ▼
框架层 (serial.c) [rt_serial_write]:
    1. 把数据填入环形缓冲区
    2. 判断 DMA 还是中断模式
    3. 调用 ops->putc(ch) 发送第一个字节
    4. 后续在中断中继续发送（ISR 也是框架层的）
    5. 支持阻塞：没发完就挂起线程在 completion 上
    │                                     ↑
    │  以上 95% 的逻辑全芯片通用           │
    │                                     │
    ▼                                     │
硬件驱动 (stm32_uart.c):                   │
    ops->putc(ch) → *(USART_DR) = ch      │
    ops->getc()   → return *(USART_DR)    │
                         ↑                          
                    就这几行跟硬件有关
```

#### 7.1.4 其他设备框架一览

| 设备框架 | 共性逻辑（框架层负责） | 硬件驱动只需实现 |
|----------|----------------------|-----------------|
| **串口** | 环形缓冲、阻塞/非阻塞读写、DMA 双缓冲调度 | `putc / getc / configure` |
| **SPI** | 消息队列调度、片选管理、标准时序生成 | `xfer()` — 收发一帧数据 |
| **I2C** | START/STOP/ACK 时序编排、设备地址管理 | `send_start / send_stop / send_byte / recv_byte` |
| **传感器** | 数据上报机制（轮询/FIFO/中断）、应用层查询接口 | `fetch_data()` + 传感器寄存器表 |
| **看门狗** | 超时管理、应用层 start/stop/keepalive 接口 | `start / stop / keepalive` 寄存器操作 |
| **ADC** | 通道管理、采样参数配置接口 | `convert()` + 通道使能 |

#### 7.1.5 一句话总结

> **框架层 = 把同类 100 个芯片驱动中相同的 95% 逻辑抽出来只写一次，硬件驱动只需填写剩余 5% 的寄存器回调，注册进去即可。** 本质上是一种**模板方法模式**——框架层定义好算法骨架（怎么读/写/缓冲/调度），硬件驱动只填充具体的硬件操作步骤。

## 9. 继承与派生的设计模式总结

### 9.1 三级派生层次

RT-Thread 的内核对象体系存在三级派生：

```
第一级：rt_object                    ← 根基类（所有对象的共同祖先）
        提供：名称、类型、标志、链表节点
        │
第二级：rt_timer / rt_thread / rt_ipc_object / rt_device / rt_mempool ...
        提供：各自领域的通用抽象
        ├── rt_timer：跳表 + 超时回调
        ├── rt_thread：栈 + 状态 + 优先级 + 时间片 + ...
        ├── rt_ipc_object：挂起线程链表
        ├── rt_device：设备操作接口 + 设备分类 + 引用计数
        └── ...
        │
第三级：rt_lptimer / rt_semaphore / rt_serial_device / rt_spi_bus ...
        提供：具体类型的完整功能实现
```

### 9.2 设计优势

1. **统一管理**：所有内核对象通过 `rt_object` 的 `list` 成员挂载到全局 `rt_object_container[]`，可以用 `list_device()`、`list_thread()` 等命令遍历所有实例。

2. **统一接口**：`rt_object_init/allocate/detach/delete/find` 对所有对象类型通用。

3. **可扩展性**：新增设备类型只需：
   - 定义新的设备结构体（第一个成员为 `struct rt_device` 或 `struct rt_object`）
   - 实现 `rt_device_ops` 中的回调函数（重点是 `control()` 的私有命令）
   - 在 `rt_object_container[]` 中注册类型
   - 通过 `rt_device_register()` 注册到 I/O 设备管理层

4. **内存效率**：结构体嵌套避免了虚函数表、RTTI 等 C++ 运行时的额外开销，对象大小完全由编译时确定。

5. **类型安全**：通过 `rt_object_class_type` 枚举进行运行时类型检查，防止错误转换。

### 9.3 向上转型与向下转型

```c
// ★ 向上转型（子类 → 父类）：直接强制转换，始终安全
struct rt_device *dev = (struct rt_device *)serial_device;
struct rt_object *obj = (struct rt_object *)dev;

// ★ 向下转型（父类 → 子类）：需先检查 type 字段，确保类型匹配
struct rt_object *obj = rt_object_find("uart1", RT_Object_Class_Device);
if (obj && obj->type == RT_Object_Class_Device) {
    struct rt_device *dev = (struct rt_device *)obj;  // 安全
    // 但要进一步得到 rt_serial_device，通常需要通过 dev->user_data 或框架内部查找
}
```
